# v0.5 RFC — Auth-aware filter

> Status: **draft / awaiting review.** Boss-prioritized RFC for the
> auth-aware filter item parked at the end of
> [`docs/v0.4-spec-at-scale.md`](./v0.4-spec-at-scale.md#open-questions-parked-for-v05).
> This document is design-only — no code lands until the design is
> approved.

## ⚠ Security disclosure (read first)

**This filter is ergonomics, not a security boundary.** The user-roles
signal proposed here is **page-supplied** and **untrusted** end-to-end:
the SDK reads it from the DOM (or the integrator's own JS), forwards it
over the wire, and the bridge / backend uses it only to *narrow the
agent's tool list*. It does **not** authorize the underlying tool
invocation.

A web-companion-integrated app **MUST** independently enforce its real
authorization on the actual click / fetch / mutation that a tool's steps
trigger — the same way it would for any HTTP request from a logged-in
browser. The filter exists to:

- reduce the agent's token cost (fewer irrelevant tools in the catalog),
- reduce agent confusion (the model won't try `account.delete` for a
  read-only viewer),

and that's it. If an attacker forges `userRoles: ['admin']`, the worst
they get is a more permissive catalog — they still hit your real RBAC
when they try to actually execute the tool. Don't put security-critical
filtering here; keep it at the server boundary.

## Why this is the v0.5 headliner

v0.4 already split the catalog into flows and added a `where:` predicate
(url + marker). That handles "different page → different tool subset",
which is the *navigation* axis of scale. But a 100-flow production app
also faces an *identity* axis:

- An admin user sees `account.delete_user`, `support.escalate`,
  `support.refund_order`; a regular customer sees none of those.
- A logged-out visitor shouldn't see `account.logout` at all.
- A multi-tenant SaaS may have per-plan tools (`reports.export_csv` only
  for Pro plan).

Without an identity-aware filter, the agent's tool list is
*page-correct* but *role-wrong*. The agent burns context on tools that
would 403 the moment they were invoked.

v0.5's scope: extend `where:` with an optional `roles:` predicate, teach
the SDK to read user roles from the DOM (with explicit programmatic
overrides), and plumb the value through `page/changed` so bridge +
backend can filter accordingly.

## Non-goals

- **Not** building a general expression engine
  (`user.role === 'admin' && user.plan === 'pro'`). Compound predicates
  are expressed by splitting the tool across flows.
- **Not** auto-extracting roles from the JWT on the backend side. The
  page knows; the SDK doesn't speculate. If a backend mode wants to
  inject roles, it does so by having the page render them into the DOM.
- **Not** changing the wire protocol's shape beyond adding one optional
  field to `page/changed` and one optional `WhereSpec` field.
- **Not** bumping spec version. 0.5 stays at `version: '0.2'` — it's
  purely additive within the v0.2 schema.

## Design

### `WhereSpec.roles` — new optional field

```jsonc
{
  "name": "delete_user",
  "description": "Soft-delete a user account.",
  "params": {
    "type": "object",
    "properties": { "id": { "type": "string" } },
    "required": ["id"]
  },
  "steps": [ { "type": "click", "target": "[data-ai-tool='delete-user-{id}']" } ],
  "where": {
    "url": "**/admin/**",
    "marker": "[data-ai-view='admin-users']",
    "roles": ["admin"]
  }
}
```

Schema additions:

```ts
type WhereSpec = {
  url?: string;
  marker?: string;
  roles?: string[];   // NEW — length >= 1 when present
};
```

**Semantics:**

- `where.roles` is an array of role *names* (free-form strings, but
  constrained by the v0.4 identifier regex `/^[A-Za-z][A-Za-z0-9_-]*$/`
  to avoid quoting hazards).
- A tool/resource matches a user iff `userRoles ∩ where.roles ≠ ∅`.
- The check AND's with the other `where` predicates: a tool with
  `where: {url, marker, roles}` requires **all three** to pass.
- Omitting `where.roles` keeps v0.4 behavior — the tool is visible to
  any user the page-level filter lets through.
- `where.roles: []` is rejected at schema time (use "omit the field" to
  mean "anyone").

**At the index level**, `where.roles` is allowed on a `ModuleRef` and
applies to every tool/resource inside that module (merged via the same
`mergeWhere` rule we added in P2 of v0.4). This means a whole flow can
be gated by role without per-tool ceremony:

```jsonc
{
  "version": "0.2",
  "modules": [
    { "name": "admin",
      "url": "./companion/admin.json",
      "where": { "marker": "[data-ai-view='admin']", "roles": ["admin"] } }
  ]
}
```

### `PageState.userRoles` — SDK collects from DOM

`packages/sdk/src/page-state.ts` extends `PageState`:

```ts
type PageState = {
  currentUrl: string;       // pathname + search + hash (v0.4)
  matchedMarkers: string[]; // v0.4
  userRoles: string[];      // NEW v0.5 — sorted, deduped
};
```

`PageStateTracker.start()` collects `userRoles` in this priority order:

1. **Explicit override** — `attachWebSocket({ userRoles: [...] })` or
   `new PageStateTracker({ userRoles: () => [...] })`. The lambda form
   allows reactive frameworks to wire it to their auth store.
2. **`<meta name="wc-user-roles" content="admin,staff">`** — comma- or
   space-separated; for SSR'd pages without an auth-store-aware app
   layer.
3. **`<body data-wc-user-roles="admin staff">`** — same parsing as
   meta. Convenient when the DOM root reflects auth state.
4. **None of the above** → `userRoles: []` (treated as anonymous).

The tracker re-evaluates on the same triggers as `matchedMarkers`:
MutationObserver on `document.body` + `wc:location-change`. If the page
mutates `<body data-wc-user-roles>` on login/logout, the diff fires a
`page/changed` and the server pushes `notifications/tools/list_changed`
— same plumbing as v0.4 markers.

### Wire — `page/changed` gets one new field

```jsonc
{
  "type": "page/changed",
  "currentUrl": "/admin/users",
  "matchedMarkers": ["[data-ai-view='admin-users']"],
  "userRoles": ["admin"]   // NEW
}
```

Wire-level backward compatibility: a v0.4 SDK against a v0.5 server
omits `userRoles`; server treats it as `[]` (anonymous). A v0.5 SDK
against a v0.4 server: server just ignores the unknown field.
Both directions degrade gracefully.

### Server filter — `passesWhere` learns roles

`packages/sdk/src/where-check.ts` extends the predicate:

```ts
export function passesWhere(where: WhereSpec | undefined, state: CapturedPageState): boolean {
  if (!where) return true;
  if (where.url && !globMatch(where.url, state.currentUrl)) return false;
  if (where.marker && !state.matchedMarkers.includes(where.marker)) return false;
  if (where.roles?.length) {
    const has = where.roles.some(r => state.userRoles.includes(r));
    if (!has) return false;
  }
  return true;
}
```

Both `@web-companion/local-bridge` and `examples/reference-backend`
already call `passesWhere` in their `listAllTools(scope)` /
`listAllResources(scope)` paths — they get the role check for free once
`CapturedPageState` carries `userRoles`. The only change on the server
side is propagating the new field from `page/changed` into the cached
`pageState`.

### Meta tools

- **`companion_pages`** returns the new field too, so the agent can see
  what role context the user is in:

  ```jsonc
  {
    "currentUrl": "/admin/users",
    "matchedMarkers": ["[data-ai-view='admin-users']"],
    "userRoles": ["admin"],
    "currentFlows": ["admin"]
  }
  ```

- **`companion_flows`** — no shape change. A flow's `active` flag now
  also depends on role; that's already covered by `passesWhere` filtering
  the underlying tools.
- **`companion_tools(flow?)`** — no shape change. The per-tool list it
  returns is already role-filtered.

### Annotator playbook update

`docs/annotator-playbook.md` adds a section *Auth-aware tools* under
"Recommended pass over a project":

1. Find the auth source. Look for: an auth context provider, a
   `useUser()` hook, a Redux/Zustand slice with `role`, or an SSR'd
   `<body class="role-admin">`. Decide which signal is the most stable.
2. Pick one DOM surface for the SDK to read. Recommended:
   `<body data-wc-user-roles="...">` updated by the same effect that
   triggers re-renders on login/logout. Document this in the per-flow
   spec via a comment.
3. For each tool/resource the user might *not* see, decide what role
   gate to apply. Common patterns:
   - `roles: ['admin']` for destructive admin tools
   - `roles: ['staff', 'admin']` for moderator tools
   - omit `roles` for anything everyone sees
4. Hoist common gates to the module level. If every tool in `admin.json`
   needs `roles: ['admin']`, put it on the `ModuleRef` instead of
   repeating it.

The 4 safety properties still hold: no business logic, plain CSS, 5 step
kinds, no `onClick` rewrites. We're only adding *visibility* metadata,
never *enforcement*.

### Backward compatibility — guarantees

1. **Existing v0.2 specs continue to parse and run unchanged.**
   `where.roles` is optional; absence preserves v0.4 behavior.
2. **v0.4 SDK against v0.5 server**: client sends `page/changed` without
   `userRoles`; server treats as `[]`. Tools with `roles` configured
   become invisible (correct fail-closed behavior — the page apparently
   doesn't know what role the user has).
3. **v0.5 SDK against v0.4 server**: server ignores the extra
   `userRoles` field and applies v0.4 filtering only. Tools with `roles`
   are visible regardless of role — slightly over-permissive but safe
   (real RBAC at the server is still enforced; see the security
   disclosure).
4. **`scope: 'all'` bypass remains the escape hatch.** Agents that
   explicitly want the unfiltered catalog get it, same as v0.4.

### Schema changes summary

- `whereSchema.roles`: `z.array(identifierSchema).min(1).optional()`
- `companion.schema.json` regenerated by `pnpm gen-schema`
- No new schema for `userRoles` on the wire — it's just an array of
  strings on `page/changed`. (Wire types live in
  `packages/sdk/src/ws-client.ts`'s message union; add the optional
  field there.)
- No version bump. Still `version: '0.2'`.

## Open implementation questions

1. **Should `userRoles` be ordered or set-shaped on the wire?** Stay
   `string[]` for JSON simplicity; internally normalize to deduped+sorted
   before diffing so `["admin", "staff"]` and `["staff", "admin"]` don't
   thrash `page/changed`.
2. **Should the SDK re-emit `page/changed` on every poll, or only on
   diff?** Same as v0.4 — only on diff. Initial `page/changed` after
   handshake establishes the baseline.
3. **Anonymous-user UX.** If `userRoles: []` and every tool has
   `roles: [...]`, the catalog will be empty. Should the SDK warn? Punt
   to runtime telemetry, not RFC scope.
4. **`role` (singular, string) as a convenience?** Stay strict —
   require `string[]`. We've seen the singular-vs-plural ambiguity bite
   in other specs; one shape is enough.
5. **Should `where.roles` support negative match (`"!admin"`)?** Punt to
   v0.6 if the need shows up. For now, split the tool into two specs
   with different `where` if you really need "everyone except".

## What we're explicitly NOT doing

- **No expression DSL.** No `where: { predicate: "user.plan === 'pro'" }`.
  If you need compound conditions, split the tool.
- **No backend-side role injection.** Backends that want to influence
  the role signal do so by rendering it into the page, not by patching
  the wire.
- **No per-step or per-param-value role checks.** Role applies at
  tool/resource visibility level. Param-value-aware authorization
  (`delete_user(id)` allowed for own id, not others') is enforcement
  territory, not catalog-filter territory.

## Alternatives considered

- **`where.predicate: "user.role === 'admin'"`** — rejected. Adds a
  parser, a sandbox, and a new failure mode; benefit is a marginal
  expressiveness gain over `roles: [...]`.
- **`where.requiresAuth: true`** — rejected. Too coarse; doesn't
  distinguish admin from staff from logged-in-user.
- **Capability bag (`requires: ['admin-perm']` separate from `where`)**
  — rejected. Two filter axes parallel to each other create surprising
  intersection rules. One predicate kind, one merge rule.
- **Auto-deriving roles from JWT in the backend mode** — rejected.
  Breaks the SDK/backend symmetry (bridge mode has no JWT). The page
  always has the most up-to-date view of "who is logged in right now".

## Migration recipe (0.4 → 0.4 + roles)

1. Decide your auth source. For most React apps, the cleanest path is:
   ```jsx
   <body data-wc-user-roles={user?.roles.join(' ') ?? ''}>
   ```
2. In `companion.json` modules, add `where.roles: [...]` to any
   tool/resource that's role-gated. Hoist common gates to the
   `ModuleRef.where` level.
3. Re-run `pnpm gen-schema` (if you're tracking JSON schema externally).
4. Open the page, log in/out with different roles, confirm
   `companion_pages` returns the expected `userRoles` and the catalog
   shrinks/grows accordingly.

That's the whole upgrade. No spec version bump, no SDK API breakage.
