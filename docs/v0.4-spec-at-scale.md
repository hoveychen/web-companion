# v0.4 Design Doc — Spec at Scale + Context Management

> Status: **frozen** for v0.4 implementation. Changes after P0 lands need a
> follow-up amendment commit referencing this section so P1–P9 stay aligned.

## Why

v0.3 ships a SDK + control plane that's fundamentally **toy-grade for any
non-trivial site**:

- One flat `companion.json` with a single tool array. 100 flows → 5K lines of
  JSON shipped to every page load, every `tools/list` call.
- Agent sees every tool always — token bloat, name collisions
  ("submit" on 5 pages), decision-quality dilution.
- `where:` is evaluated runtime-only (fail-on-invoke), not as a catalog
  pre-filter. The agent doesn't get told "you can't use those right now".
- The agent can't even ask "where am I?" or "what flow am I in?" — there's
  no context primitive in the protocol.

v0.4 fixes the protocol so 100+ flows / 50+ pages becomes a viable shape.

## Glossary

| Term | Meaning |
| --- | --- |
| **Flow** | A named group of related tools/resources (e.g. `checkout`, `search`). Identified by a `name` that's also the namespace segment of every tool inside it. |
| **Module** | A separate JSON file declaring one flow's tools/resources. Loaded lazily via `$ref` from the index `companion.json`. |
| **Index** | The top-level `/.well-known/companion.json`. Lists `modules` to load, plus optional site-level tools/resources without a flow. |
| **Scope** | The set of tools/resources the agent currently sees. Default scope = `where`-passing for current `pageState`. `_meta.scope: 'all'` overrides to full catalog. |
| **pageState** | `{ currentUrl: string, matchedMarkers: string[] }`, maintained by the SDK and pushed to bridge/backend on every navigation. |

## Schema 0.2

```ts
type CompanionSpec = {
  version: '0.1' | '0.2';
  modules?: ModuleRef[];          // 0.2 only
  tools?: ToolSpec[];             // site-level tools (no flow)
  resources?: ResourceSpec[];     // site-level resources (no flow)
};

type ModuleRef = {
  name: string;                   // flow name; must match /^[A-Za-z][A-Za-z0-9_-]*$/
  url: string;                    // resolved against the parent doc's URL
  description?: string;           // shown by `flows` meta tool
  where?: WhereSpec;              // applied to every tool/resource inside;
                                  // module-internal where: AND'd with this
};
```

`ToolSpec` / `ResourceSpec` / `WhereSpec` are unchanged from 0.1.

A module file is a `CompanionSpec` itself — same schema, but `modules` MUST
be empty (no nested modules in 0.2; revisit in v0.5 if needed). Inside a
module, every tool/resource implicitly inherits the parent's flow name as
its namespace.

## Namespacing

- Tool `name` inside a spec file: `[A-Za-z][A-Za-z0-9_-]*` (no `.`).
- Surfaced tool name (what the agent / MCP client sees):
  - Site-level tool: `<toolName>` (no namespace)
  - Tool inside module `foo`: `foo.<toolName>`
- `.` is the only allowed namespace separator. Validators reject `.` in raw
  tool names.
- Cross-module duplicate detection: two modules can both have `submit` —
  they surface as `checkout.submit` / `search.submit`, no conflict.
- Site-level vs module: a site-level `submit` plus a module `checkout.submit`
  is fine. Two site-level `submit`s in the same index is a parse error.

`runtime.invokeTool(name, input)` accepts either form:
- `runtime.invokeTool('checkout.submit', …)` → routes to module's tool
- `runtime.invokeTool('submit', …)` → routes only to site-level tool, never
  ambiguous to a module's

## Loader

Pseudocode:

```ts
async function load(rootUrl) {
  const visited = new Set<string>();
  const queue = [{ url: rootUrl, parentWhere: undefined, flowName: undefined }];
  const flat: Array<ResolvedItem> = [];

  while (queue.length) {
    const { url, parentWhere, flowName } = queue.shift()!;
    if (visited.has(url)) throw new Error(`cycle: ${url}`);
    visited.add(url);

    const spec = await fetchJson(url);
    parse(spec);                                // throws on schema fail

    for (const t of spec.tools ?? []) {
      flat.push({
        flow: flowName,                         // undefined for index-level
        tool: { ...t, where: andWhere(parentWhere, t.where) },
      });
    }
    for (const r of spec.resources ?? []) {
      flat.push({ flow: flowName, resource: { ...r, where: andWhere(parentWhere, r.where) } });
    }

    for (const m of spec.modules ?? []) {
      const absUrl = new URL(m.url, url).href;
      queue.push({
        url: absUrl,
        parentWhere: andWhere(parentWhere, m.where),
        flowName: m.name,
      });
    }
  }
  return flat;
}
```

Error handling: per-module fetch failure surfaces through an
`onModuleError(name, err)` hook (default = console.warn). The runtime keeps
running with the successfully loaded subset — partial catalogs are still
useful. Index parse failure is fatal.

## Wire protocol additions

### sdk → server (new)

```jsonc
{
  "type": "page/changed",
  "currentUrl": "https://shop.example/cart",
  "matchedMarkers": ["[data-ai-view='cart']"]
}
```

Emitted on:
- ws `open` (after `session/hello`, before `tools/list`)
- `popstate` / `pushState` / `replaceState`
- MutationObserver detects `matchedMarkers` set diff
- explicit `runtime.refreshPageState()` call

Frequency-limited to one emit per animation frame; the diff is computed
client-side so unchanged states don't waste bytes.

### server → MCP client (new)

When server-side filter result for a session changes (page navigation,
spec hot-reload, etc.), emit standard MCP:

```
notifications/tools/list_changed
```

No payload — the client re-pulls `tools/list`. The filtered list is
returned by default.

### MCP `tools/list` opt-out filter

Default response = `where`-passing tools only (for the user's current
session, joined across `currentUrl` + `matchedMarkers`).

To get the full catalog:

```jsonc
{
  "method": "tools/list",
  "params": {
    "_meta": { "scope": "all" }
  }
}
```

The bridge/backend treats `_meta.scope === 'all'` as "skip filter". Any
other value of `_meta.scope` (`'page'`, undef, etc.) = default behavior.

## Filter algorithm

For each `(tool|resource, pageState)`:

```
passes(item, pageState) =
  item.where === undefined
  || (item.where.url   matches glob(pageState.currentUrl)
       AND item.where.marker  in   pageState.matchedMarkers)
```

`url` and `marker` are AND'd within a `WhereSpec` (same as v0.3). Module's
parent `where` was already AND'd into each item at load time, so no
re-walking needed at filter time.

Cache: bridge/backend memoize `filter(catalog, pageState) → ToolSpec[]` keyed
by `(currentUrl + sorted markers)` to avoid re-filtering on every MCP
`tools/list`. Invalidate on `page/changed`.

## Meta tools

All three are namespace-free (no flow). Registered by bridge AND backend.

### `pages`

```jsonc
// input
{ "type": "object", "properties": {} }

// output
{
  "currentUrl": "https://shop.example/cart",
  "matchedMarkers": ["[data-ai-view='cart']"],
  "currentFlows": ["checkout", "nav"]    // flows with at least one matching item
}
```

### `flows`

```jsonc
// input
{ "type": "object", "properties": {} }

// output (array)
[
  {
    "name": "checkout",
    "description": "Cart + checkout flow.",
    "where": { "url": "**/cart", "marker": "[data-ai-view='cart']" },
    "toolCount": 4,
    "resourceCount": 1,
    "active": true                         // matches current pageState
  },
  …
]
```

### `tools(flow?)`

```jsonc
// input
{
  "type": "object",
  "properties": {
    "flow": { "type": "string", "description": "Optional flow name to drill into; omit for the full active-page tool list." }
  }
}

// output (array of {name, description, params?})
[
  { "name": "checkout.submit", "description": "Place the order.", "params": {…} },
  …
]
```

`tools()` with no flow = current `pageState`-scoped active tools.
`tools(flow: 'search')` = all tools in `search` module regardless of current
page (useful when agent is preparing to navigate).

## Backward compatibility

- A `companion.json` with `version: '0.1'` and no `modules` field
  continues to parse — treated as a single anonymous module with no flow
  name. Every tool is site-level.
- A `version: '0.1'` file MAY NOT declare `modules` — parser rejects.
- Switching to `version: '0.2'` is opt-in; nothing in the runtime / bridge /
  backend implicitly requires it.
- `notifications/tools/list_changed` is harmless to clients that ignore it
  (per the MCP spec).
- `_meta.scope` is a MCP-level optional field; clients that don't set it
  get filtered results, which is the v0.4 default.

## Migration: 0.1 → 0.2

For a site with N flows of M tools each (currently in one flat
`companion.json`):

1. Bump `version` to `'0.2'`.
2. For each conceptual flow, pull out its tools/resources into a new file
   `companion/<flowName>.json` with `version: '0.2'` and `modules: []`.
   Tool names stay raw (no `flowName.` prefix in the file — the prefix is
   applied by the loader).
3. Replace the moved entries in `companion.json` with a single
   `modules: [{ name: '<flow>', url: './companion/<flow>.json', where: {...} }, …]`
   entry per flow. Move each flow's shared `where:` up to the module ref.
4. (Optional) Add per-flow `where:` if you haven't already — this is what
   activates the server-side filter.

Annotator's `--out-dir` mode (v0.4 P6) produces this layout from scratch.

## Open questions parked for v0.5

- Nested modules (modules referencing other modules).
- Per-module variable interpolation (e.g. base URL prefixes).
- Auth-aware filter (agent only sees tools the current user is allowed to
  invoke).
- Streaming `tools/list` (page-by-page) for catalogs > 1000 tools.
