# v0.6 RFC — Nested modules

> Status: **draft / awaiting review.** Boss-prioritized RFC for the
> nested-modules item parked at the end of
> [`docs/v0.4-spec-at-scale.md`](./v0.4-spec-at-scale.md#open-questions-parked-for-v05).
> Design-only — no code lands until the design is approved.

## Why this is the v0.6 headliner

v0.4 introduced one level of `modules`: an index `companion.json`
references a set of `companion/<flow>.json` files, each containing
flat `tools[]` / `resources[]`. Surface names are namespaced as
`<flow>.<tool>` — namespaced enough that 30–50 flows stay
manageable. Past ~50 flows, the flat index turns into a wall of
indistinguishable `ModuleRef` entries, and the spec stops being a
scalable artifact.

Real-world web apps have **hierarchy**. AWS console groups services
("Compute → EC2", "Compute → Lambda", "Storage → S3"). Shopify groups
admin around "Orders / Customers / Products / Analytics / Settings",
each with sub-flows. A 100+ flow catalog without grouping is
unreadable both to a human spec maintainer and to an agent
enumerating with `companion_flows`.

v0.5 added the **identity axis** (`where.roles`) on top of the
already-existing page axis (`where.url`, `where.marker`). v0.6 adds
the **hierarchy axis** — the third independent dimension along which
catalogs scale.

Without it, the only escape valve is naming convention (a flat
`module_ecommerce_checkout` instead of `ecommerce.checkout`), which
the protocol doesn't help with and which agents can't navigate
without explicit awareness.

## Non-goals

- **Not** removing the v0.4 `flow.tool` namespace shape. v0.6
  *extends* it to `flow.subflow.tool` etc., it doesn't change the
  one-level case.
- **Not** introducing nested *types* (still: `ToolSpec`,
  `ResourceSpec`, `ModuleRef`). Only nested *references*.
- **Not** removing the per-file `version: '0.2'` shape. Schema stays
  at 0.2 — this is purely a loader-side capability change with one
  small schema relaxation.
- **Not** introducing variable interpolation, dynamic resolution, or
  any computed module URLs. URLs stay literal strings.

## Design

### Schema — one removed restriction

v0.4 P1 added a `.strict()` to `v02SpecSchema` so unknown keys would
error. The same P1 also made it possible to declare `modules` at the
top level. **v0.4 didn't disallow `modules` inside a sub-module
file** — the schema would accept it. The *loader* refuses to recurse
into nested modules and throws `nested modules forbidden in v0.2`.

v0.6's schema is the same v0.2 schema, unchanged. The loader's
`nested modules forbidden` guard is removed (replaced by a
configurable depth cap, see below). That's the entire schema-level
delta — additive at the protocol layer, no version bump, no breaking
field, no breaking deserialization.

### Surface naming — `.` for every level

A tool named `submit` inside a module named `checkout`, inside a
module named `ecommerce`, surfaces to the agent as:

```
ecommerce.checkout.submit
```

The `.` separator is what v0.4 reserved. Tool / resource / module
*identifiers* still match `/^[A-Za-z][A-Za-z0-9_-]*$/` — no `.`
allowed at any level. Joining is purely the loader's responsibility.

Conflict rules:

- Two `ModuleRef`s under the same parent with the same `name` →
  rejected at schema time (already enforced via P1
  `rejectDuplicateNames`).
- `cart.submit` and `ecommerce.cart.submit` → coexist. Different
  paths, different surface names.
- `cart.submit` (declared in `cart.json`) and a sibling tool named
  `cart.submit` (literally that string) in the site-level `tools[]`
  → impossible because `.` isn't a legal identifier character.

### Loader — BFS queue with parent-path stack

The v0.4 P2 loader is already a BFS with `Frame { url, parentWhere,
flowName?, moduleEntry? }`. v0.6 extends the frame:

```ts
type Frame = {
  url: string;
  parentWhere: WhereSpec | undefined;
  parentFlowPath: string[];     // NEW: chain from root, e.g. ['ecommerce', 'checkout']
  moduleEntry?: ModuleRef;
};
```

When the loader fetches a frame's spec, for each declared
`modules: ModuleRef[]`:

1. `name` is validated as an identifier (existing P1 grammar).
2. `parentFlowPath.length + 1 > maxDepth` → record an
   `onModuleError` ("depth exceeded") and continue (don't queue).
3. Otherwise enqueue a child frame:
   - `url`: resolved against the parent's URL (same as v0.4)
   - `parentWhere`: `mergeWhere(currentFrame.parentWhere, ref.where)`
     (deep merge, child wins per field — existing v0.5 logic)
   - `parentFlowPath`: `[...currentFrame.parentFlowPath, ref.name]`

For each tool/resource inside a frame:

- Surface name = `[...parentFlowPath, item.name].join('.')`
- `where` = `mergeWhere(parentWhere, item.where)`

Cycle detection (existing `visited: Set<absUrl>`) is unchanged —
a same-URL fetch attempt anywhere in the tree skips, regardless of
depth. The visited set is per-load, not per-branch, so a module
shared by two parents is fetched once and its tools surface under
*both* parent paths (this is intentional — a shared utility flow
reused across hierarchies).

### `maxDepth` — configurable, default 3

```ts
type LoaderOptions = {
  // existing
  fetch?: typeof fetch;
  onModuleError?: (info: ModuleErrorInfo) => void;
  // NEW v0.6
  maxDepth?: number;  // default 3
};
```

Rationale for the default:

- **1** = current v0.4 behavior (`module.tool`, no further nesting).
  Useful as a constraint when migrating cautiously.
- **2** = `domain.flow.tool` — two-tier grouping. Fits most large
  apps (admin / public / partner; products / orders / customers;
  etc.).
- **3** = `domain.flow.subflow.tool` — covers the deepest real-world
  hierarchy I've seen in production catalogs. Anything beyond is
  almost always a sign the catalog should be flattened.
- **> 3** = developer-explicit opt-in; the loader allows it but the
  decision lives in the integrator's `LoaderOptions`, not the
  default.

`maxDepth` is a *loader* setting, not a *spec* setting. A spec
author writes whatever depth they want; the runtime decides how
much to follow. This avoids needing a spec-side `maxDepth: 3` field
that every author would have to set.

### `mergeWhere` — already recursive-friendly

v0.5's `mergeWhere(parent, child)` is per-field with child-wins
fallback to parent. Recursive use over a stack:

```
mergeWhere(mergeWhere(grandparent, parent), child)
```

is associative-enough for the use cases here — each step inherits
the most-recently-set value of each field. The BFS loader does this
naturally because it merges as it descends. No code change.

### Meta tools — surface paths, stay flat

The three v0.4 meta tools keep their shapes — agents that read
v0.4 schemas don't break — but the strings inside become richer.

- `companion_pages.currentFlows` → now contains the deepest active
  segment, e.g. `['ecommerce.checkout', 'support.tickets']`. The
  segment count = nesting depth - 1. Older parsers split on `.` to
  get the leaf flow; v0.6 parsers can split fully.
- `companion_flows` → each entry's `name` is now the full path
  (`ecommerce.checkout`), and the entries are sorted lexicographically.
  Adds an optional `parent` field (`'ecommerce'` for the example;
  absent for root-level flows). Adds an optional `depth` field
  (`1` for root, `2` for one nested level, etc.) for renderers
  that want to indent.
- `companion_tools(flow?)` → `flow` is a path prefix. Passing
  `flow='ecommerce'` returns tools whose surface name starts with
  `ecommerce.` (i.e. any descendant). Passing
  `flow='ecommerce.checkout'` narrows further.

Adding fields, not changing shapes, keeps v0.4 and v0.5 agents
compatible — they just see strings with extra dots and ignore the
new optional fields.

### What if a server lies about depth?

The bridge / backend trust the SDK's reported pathnames. They have
to — surface names are computed by the loader, then forwarded by
the wire. An attacker controlling the bridge could in principle
inject surface names of arbitrary depth or arbitrary content. This
is **not new in v0.6** — the same trust assumption exists in v0.4
(a malicious bridge could inject any tool name). v0.6 doesn't make
this worse; the security model still rests on "you trust the bridge
you're running locally".

## Open implementation questions

1. **Surface name length cap?** If `parentFlowPath.length` is large
   and `tool.name` is long, the full surface can exceed 64 chars,
   which is awkward for some MCP clients. Probably not worth
   capping at the protocol layer — surface this in the *playbook*
   instead (recommend short names + 2-3 deep max).
2. **Should `companion_modules` be added?** A meta tool returning
   the full tree (`{name, children: [...]}`). Probably yes, but
   carving it out as v0.7 is fine if agents can already navigate by
   prefix-matching `companion_flows`.
3. **Should `maxDepth` panic or skip?** Current proposal: emit
   `onModuleError` and skip. Alternative: throw. Skip is more
   forgiving for partial-catalog scenarios; throw is safer for
   strict deployments. Default skip, allow opt-in throw via
   `onModuleError` re-throwing.
4. **Per-module locale / branding?** A nested `support` module
   under multiple parents (`en.support`, `de.support`) is currently
   forced to live at two URLs because the visited set deduplicates.
   We could add a `dedupe: false` option to a `ModuleRef` to force
   re-fetch under each parent, but this complicates the loader
   significantly. **Punt to v0.7** if the need shows up.
5. **Cycle path in error messages.** When a cycle is detected, the
   current `onModuleError` reports the URL. With nesting it'd be
   nice to also report the path-from-root for debugging. Trivial
   addition — bundle into the same P-task.

## What we're explicitly NOT doing

- **No depth-discovery API.** Agents can compute depth by
  splitting on `.`; no need for a dedicated field on every tool.
- **No deep `where` queries.** A `where: { flow: 'ecommerce.*' }`
  predicate (any descendant) would be nice for cross-cutting
  modal flows, but it's a different filter axis and belongs in
  its own RFC.
- **No per-tool-level `version: '0.6'` opt-in.** The behavior
  change is implicit: if a v0.6 SDK loads a nested spec, it works;
  if a v0.5 SDK loads it, the loader's existing `nested modules
  forbidden` check rejects it via `onModuleError`. No version
  field to bump.

## Alternatives considered

- **Synthetic hierarchical naming convention (`module_ecommerce__checkout`)**
  — rejected. Agents can't navigate it as hierarchy without
  out-of-band knowledge; defeats the purpose.
- **Adding `parent: string` to every `ModuleRef`** — rejected.
  Couples the spec to the parent's existence, makes refactoring
  fragile, and creates two ways to express the same thing.
- **A separate `submodules` field different from `modules`** —
  rejected. Same shape, same semantics; needless distinction.
- **Unbounded depth (no `maxDepth`)** — rejected. Allows runaway
  recursion and obscures bugs. The cap is configurable, so this
  isn't even a real restriction.

## Migration recipe (0.2 → 0.2 + nested)

1. Identify groups of related flows. If you have 30 cart-related
   flows under `cart.*`, that's a candidate for a `cart` parent.
2. Move related modules into a sub-directory:
   ```
   public/.well-known/
   ├── companion.json
   ├── companion/
   │   ├── cart.json                    # was a leaf; now a sub-index
   │   ├── cart/
   │   │   ├── view.json
   │   │   ├── edit.json
   │   │   └── checkout.json
   │   └── support.json
   ```
3. In `companion/cart.json`, replace the inline `tools[]` /
   `resources[]` with a `modules[]` array referencing the sub-flows:
   ```jsonc
   {
     "version": "0.2",
     "modules": [
       { "name": "view", "url": "./cart/view.json" },
       { "name": "edit", "url": "./cart/edit.json" },
       { "name": "checkout", "url": "./cart/checkout.json" }
     ]
   }
   ```
4. Existing tool surface names that were `cart.add_to_cart` become
   `cart.view.add_to_cart` (or wherever the tool ended up).
   **Agents that hardcoded the old name will break** — this is the
   only externally visible behavior change. Treat it like a
   namespace migration: announce in your changelog, ship both forms
   for one release if you need a transition window.
5. Bump the runtime's `maxDepth` if you go past 3.

That's it. The wire protocol doesn't change; the schema doesn't
change; the only thing that changes is the loader respects the
nesting.
